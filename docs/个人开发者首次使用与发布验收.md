# Kodrix Code：个人开发者首次使用与发布验收

本文面向首次使用 Kodrix Code 的个人开发者，也作为每个正式版本发布前的验收清单。目标是让用户从安装完成走到第一条 AI 回复，并明确本地模型、云端模型和开发环境各自需要准备什么。

## 普通用户：安装后开始使用

普通用户应安装项目发布的 Kodrix Code 安装包。Node.js、npm、Gulp 和源码编译属于参与项目开发或从源码运行时的要求，不应成为使用已发布安装包的前置条件。

首次启动后，可从欢迎菜单进入“新手使用向导”，也可选择“配置 AI 模型”。建议按以下顺序完成：

1. 选择云端模型或本地模型，并准备对应的服务地址、模型名和 API Key（若服务商要求）。
2. 在“AI 供应商管理”中添加或选择预设，检查模型列表并运行连接测试。
3. 连接测试通过后，将该供应商设为当前供应商；在 Chat 模型列表中选择 Kodrix 提供的模型。
4. 先发送一条普通聊天请求，确认模型确实能生成回复；再单独验证 Agent 工具调用和项目文件修改。
5. 如果从 Cursor 导入配置，确认导入结果后再检查供应商、密钥和模型路由。

连接测试通过只表示测试模型完成了一个最小聊天请求。Agent 工具调用、视觉输入和其他模型能力还取决于模型本身、服务端配置和具体接口支持情况。

## 本地模型

### Ollama

- 默认服务地址：`http://127.0.0.1:11434`。
- 先在 Ollama 中下载并启动模型，再在 Kodrix 中选择相同的模型 ID。
- 连接测试会读取模型列表，并实际请求选定模型；没有可测试模型时应显示失败，而不是只报告服务已连接。
- 首次加载模型可能较慢。测试最多等待 10 秒读取模型列表，再等待最多 60 秒请求模型。

### llama.cpp

- 内置预设默认地址：`http://127.0.0.1:8080/v1`。
- 先启动提供 OpenAI 兼容 `/v1/models` 和 `/v1/chat/completions` 接口的 `llama-server`，再在 Kodrix 预设中选择服务实际返回的模型 ID。
- 使用自定义端口或需要 API Key 时，改用自定义 OpenAI 兼容供应商并填写准确的 `/v1` 地址。
- 工具调用是否可用取决于所用模型的 chat template 和服务端配置。若普通聊天成功但 Agent 不调用工具，应先核对这两项。

## 云端模型

1. 从供应商官方控制台创建 API Key，并选择与供应商文档匹配的预设或兼容接口。
2. 将 Key 输入 Kodrix 的供应商设置，不要把它粘贴到工作区文件、工单、截图或诊断文本中。
3. 测试所选模型并发起普通聊天。若服务商自定义了接口路径、模型别名或 Key 格式，按服务商要求填写。
4. 供应商不兼容工具调用时，可继续用于普通聊天，但不要将其标记为 Agent 工具调用已验收。

## 从源码运行：仅供贡献者

源码开发环境以仓库根目录的 `.nvmrc` 和 `AGENTS.md` 为准：Node.js 需与指定版本同一 major 且不低于指定版本；npm major 需小于 12。Windows 调试入口包括 `debug.bat`，完整重编译入口包括 `debug-rebuild.bat`，安装包构建入口包括 `build.bat`。

首次完整构建可能需要较长时间，尤其是 Copilot 扩展打包和 Electron 下载。执行前应确认依赖安装完成、磁盘空间充足，并按 `REPAIR-NOTES.md` 排查 native 模块和启动问题。普通用户安装已发布版本不应要求执行这些步骤。

## 正式发布验收清单

每项记录版本号、执行日期、执行人、环境和结果；失败项不得标记为通过。

### P0：发布阻断项

- [ ] 在干净的受支持 Windows 环境中安装发布包；验证首次启动不需要 Node.js/npm，不依赖开发机缓存或源码目录。
- [ ] 从欢迎入口完成供应商设置、模型选择、供应商激活、Chat 中选择 Kodrix 模型和首条成功回复。
- [ ] 分别对发布声明支持的云端、Ollama 和 llama.cpp 配置执行真实聊天；记录服务版本、模型 ID 和结果。
- [ ] 验证 API Key 错误、模型 ID 错误、模型列表为空、服务未启动、超时及 HTTP 错误均有明确提示。
- [ ] 对发布声明支持 Agent 工具调用的模型执行一次工具调用，并确认用户能审查应用到工作区的修改。
- [ ] 发布包具有明确的产品版本、变更说明、下载位置和校验信息；按目标渠道确认签名及安全扫描状态。

### P1：推广前闭环

- [ ] 新手向导能够到达供应商设置，并说明本地服务安装、启动和模型 ID 的来源。
- [ ] 明确列出每个发行渠道和操作系统的支持范围、最低硬件/系统要求及已知限制。
- [ ] 在旧版本配置上升级，验证供应商、模型路由和密钥仍可用；验证 Cursor 导入失败时原配置不被破坏。
- [ ] 按真实故障更新 `README.md`、`REPAIR-NOTES.md` 和个人开发者上手说明，并确保用户能从欢迎入口或产品文档找到它们。
- [ ] 核对剪贴板诊断内容仅含必要的版本、平台和错误类型；不得包含 API Key、提示词、工作区路径或文件内容。

### P2：持续打磨

- [ ] 为模型下载和长时间加载显示进度或下一步建议；区分普通聊天、工具调用和多模态能力。
- [ ] 提供不含敏感配置的用户反馈模板、问题追踪入口、版本历史和已知问题页面。
- [ ] 检查首次使用流程的键盘可达性、屏幕阅读器标签、中文文案和错误提示一致性。
- [ ] 每次发布后记录安装、升级、回滚和卸载结果，并把重复出现的问题转化为自动化检查或修复说明。

## 隐私与问题反馈

分享问题时只提供 Kodrix 版本、操作系统、服务类型、模型 ID、发生时间和脱敏错误信息。不要提交 `config.json`、密钥、完整请求日志、提示词或包含私人代码的截图。当前激活失败提示中的“复制脱敏诊断信息”仅复制版本、编辑器版本、平台和错误类型。

提交问题时可使用以下模板：

```text
Kodrix 版本：
操作系统/版本：
供应商类型（云端 / Ollama / llama.cpp）：
模型 ID（可脱敏）：
复现步骤：
预期结果：
实际结果：
HTTP 状态码或脱敏错误类型：
是否可稳定复现：
脱敏诊断信息：
```

请勿在模板中填写 API Key、Authorization 请求头、提示词、工作区路径或源代码内容。
